qn 1. To run this project on a fresh machine, first clone the repository using git clone <your-repo-url> and navigate into the project folder using cd <your-project-folder>. Since this is a pure frontend project built with HTML, CSS, and JavaScript, no additional dependencies or installations are required.
To start the application, you can either use the VS Code Live Server extension by opening the project and clicking “Open with Live Server” on index.html, or you can use a simple Python server by running python -m http.server 5500. After starting the server, open your browser and go to http://localhost:5500 to view the application.

qn 2. I chose to build this project using vanilla JavaScript, HTML5, and CSS3 along with the GitHub REST API. This stack was selected because it provides full control over DOM manipulation and styling without the overhead of frameworks or build tools. Since the project is relatively small and focused on API data visualization, using a lightweight stack makes the implementation more transparent and easier to debug.
A heavier framework like React or Angular would have been a worse choice for this project because it would introduce unnecessary complexity such as component architecture, bundlers, and build configurations. These tools are more suitable for large-scale applications, whereas this project benefits from simplicity and direct control over the UI rendering logic.


qn 3. One important edge case handled in this project is when a GitHub user has no detected programming languages in their repositories. This situation occurs when a user either has no public repositories or their repositories do not contain language metadata. This case is handled in the renderCard function inside ui.js.
Instead of attempting to map over an empty or undefined array, the code checks whether analysis.languages.length exists. If it does, it renders the language badges; otherwise, it displays a fallback message saying “No languages”. Without this handling, the application would either crash due to calling .map() on an undefined value or render an empty section, which would break the visual consistency of the UI.

Honest gap -  One limitation in my submission is that I originally wanted to build a more user-driven comparison feature where the user could input specific skills or programming languages they are interested in. The idea was to allow the system to not only compare two GitHub users, but also evaluate them based on whether they match the user’s selected preferences, such as prioritising certain languages or skill sets for a project.
However, I did not have enough time to fully implement this feature, so I simplified the project to focus on comparing two users based on their existing GitHub data. Instead of filtering or weighting users based on selected skills, the current version only displays the languages present in their repositories and uses that as part of the scoring breakdown.
If I had more time, I would extend the system to include a filter or preference input panel where users can select desired languages or skills, and then adjust the scoring algorithm to rank GitHub profiles based on how closely they match those preferences. This would make the tool more useful for real-world scenarios like choosing collaborators for a project.
